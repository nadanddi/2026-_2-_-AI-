**핵심 계산은 사전식과 일치한다. 실행 전에는 ID·NULL 관문을 보완하는 편이 좋다.** 검토 대상은 `ec_nested_high_specialist_20261004_v1/run.py` SHA256 `644b5e4a8176ef48760633ea7bbd168688739b879f53ad6c865a96f1cd73e040` 및 `preregistration_v1.md`다. 원 스크립트를 import/실행하지 않고 AST로 helper만 분리해 합성자료에서 계산했다. 예측모델링·분석검증 스킬의 누수/독립산술 항목을 적용했으며 새 학습·새 예측 점수·원시 train_y·EL1·잠금·test 작업은 없다.

gate는 `clip(shrink(R3raw),fulltrain bounds)`의 farm/day별 0..h 평균이다. sp는 hightrain 범위로 별도 clip하며 d의 .8은 한 번만 들어간다. inner actualbase는 `.8R3raw+.2PFNbag`를 합친 뒤 shrink/clip한다. w는 게이트0을 포함한 전체 innerquery 행수로 mean을 계산하며 λ.01/[0,.5]/KKT 부호도 맞는다. 두 farm·섞인 hour의 합성 prefix 6행은 수동합 및 Decimal과 최대차0이었다. 비중의 내부해 1/6, 0, 상한.5, d전부0→0 네 경계를 독립 Decimal 계산과 대조했다. 이는 계산식 확인이고 새안의 효용 확인은 아니다. 근거: `check_nested_code_v1.py`, `nested_code_check_v1.json`.

1. **ID/NULL 관문을 실제 학습보다 앞에 더 엄격히 둔다.** `full_inner`의 set 포함관계는 중복과 선택 누락을 놓친다. 중복된 innertrain2행/query2행 및 그에 맞는 PFN context를 넣자 현재 helper가 그대로 통과하는 합성 반례를 재현했다. 실제 완료18 CPU 캐시에서는 중복0이고 원 `E_{validator}_{fold}_cpu.npz`의 ordered inner_train_id/query ID와 모두 같았다. 즉 현재 오류가 발생했다는 증거는 없지만 관문의 빈틈은 확인됐다. 남은4 CPU도 완료 후 이 ordered ID 대조를 실행한다. 또는 사전등록된 동일 선택 규칙으로 정확한 예상 ID를 재구성한다. nonempty·row_id 유일성·farm/day/hour 유일성·키 NULL0·유한 target/bounds도 선행 확인한다. 기존 입력 특징의 MASK NaN은 정상이라 전체 feature NaN0을 요구하지 않는다. `preflight`의 OOF 83160행/중복0만으로는 정확한 예상 fold×seed×row 집합과 각 CPU/PFN 파일의 일치가 증명되지 않는다. 완전한 예상 key 집합·seed/validator·finite를 대조하고, outer reference의 label/key/finite도 specialist를 fit하기 전에 확인한다. source SHA와 `fit_audit status=PASS`는 이런 데이터 대응 검사의 대체물이 아니다.

2. **fallback 감사 분기를 사전 정책과 맞춘다.** `specialist`의 hightrain<2일 분기는 fallback 복사와 model=None을 정확히 반환한다. 하지만 첫 DIAG0/seed7 재학습 감사에서 두 model이 모두 None이 아니라고 단정해, fallback이 필요한 자료에서는 선언한 정책대로 후보를 계산한 뒤 검증이 실패한다. 실제 공개 캐시에서 첫fold hightrain>=.8은 inner28일·outer40일로 이 문제는 현재 첫fold에 발동하지 않는다. 모델이 None이면 재학습 감사를 건너뛰고 `fallback==R3S`와 해당 단계 direction0을 확인한다. inner fallback이면 inner 방향이 전부0이므로 w0도 확인한다. outer fallback만 발생했다면 이미 inner에서 학습한 w가 양수일 수 있으므로 w0을 강제하지 않는다. 이러한 분기별 감사가 예방 보완으로 적절하다. 이 수정은 현재 자료의 예측식을 바꾸는 모델 변경은 아니다. 근거: `check_nested_public_cache_v1.py`, `nested_public_cache_check_v1.json`.

3. **감사 기록과 재개 시 파일 검증을 보강한다.** w는 매 cell의 NumPy/`fsum` 및 KKT 대조로 검증되지만 num/den/gradient와 inner e/d 또는 원래 inner baseline/sp 배열을 저장하지 않아 사후 독립 재계산이 어렵다. 최소 충분 통계와 inner ID/hash를 남기면 weight와 평균행수 분모를 다시 감사할 수 있다. 사전문서의 flag 독립일수·w 경계빈도·분포 기록은 현재 row CSV에서 일부는 재계산할 수 있지만 inner는 flag행수/평균만 저장한다. 필요한 inner 진단도 저장하거나 사전문서의 약속 범위를 정확히 맞춘다. 또한 dest.exists이면 검사 없이 skip하고 audits에는 이번에 새로 만든 cell만 넣으므로, 중단 후 재개하면 부분 CSV를 지나치거나 완료 fit_audit가 전체66cell이 아닌 기록이 될 수 있다. 재개할 때 기존 cell의 key/행수/finite/weight/source 대응을 검증하고 전체66cell audit를 취합한다. 첫 실행의 계산 오류와 구분되는 재현성 경계다.

outer specialist를66개 모두 새 fit하는 결정은 HM1 provenance 문제를 해소한다. HM1과의 수치 일치를 감사로 사용하는 방식도 적절하다. 다만 과거 HM1 값이 안 맞으면 현재 코드가 assert로 중단한다는 운영 정책을 유지한다면 그 경우를 명시한다. 실제 계절v2와 inner recipe의 정합성을 지켜도 inner/outer specialist 표본량과 범위 이동은 남으며, clip 전 벌점 MSE 최적해가 clip 후 최적해가 되는 것은 아니다.
